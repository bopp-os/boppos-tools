# BoppOS boot artwork (`boppos-boot-theme`)

A black screen, the white BoppOS mark breathing slowly in the middle, and the small horizontal wordmark near
the bottom. One package, two themes.

| Installed to | What |
|---|---|
| `/usr/share/plymouth/themes/boppos/` | Plymouth splash (`boppos.plymouth`, `boppos.script`, `mark.png`, `lockup.png`) |
| `/usr/share/grub/themes/boppos/` | GRUB theme (`theme.txt`, `mark.png`, `lockup.png`) |

The logo SVGs themselves (`boppos-logo-{horizontal,stacked}-{white,black}.svg`) are in `boppos-artwork`. The PNGs
in `boot/` are rendered from them by `tools/render-boot-art` (needs `rsvg-convert`) and committed, so packaging
needs no extra tools.

**Neither theme has been run on a real boot yet.** The static checks in `tests/test_boot_theme.py` catch missing
files, unbalanced braces and undefined callbacks, not how it looks. Please run the preview below first.

## Plymouth

The package only installs the theme. Selecting it is the image's job, because the initramfs has to be built
with it. The image already installs `plymouth` and its dracut config already adds the `plymouth` module, so in the
image build, **after** `boppos-boot-theme` is installed and **before** the initramfs is generated:

```bash
plymouth-set-default-theme boppos      # writes Theme=boppos to /etc/plymouth/plymouthd.conf
```

(`cachyos-plymouth-theme` can stay installed; it just stops being the selected one.)

### Preview in a window, without installing anything

```bash
tools/plymouth-preview --check      # what is missing, if anything
tools/plymouth-preview              # opens the theme in a window; keys: b boot, t tick, p password, m message, q quit
```

It bind-mounts a scratch copy of the themes folder and a scratch `plymouthd.conf`, so nothing is installed, the default
theme is not changed and no initramfs is built; everything is unmounted again on `q` or Ctrl+C. It uses Plymouth's x11
renderer (Xwayland is fine) and needs `sudo`. Not yet run against a real Plymouth: if the window does not appear, press
`l` for the daemon log.

### Preview without rebooting

From a text console (Ctrl+Alt+F3, log in), with the graphical session stopped so Plymouth can use the display:

```bash
sudo systemctl isolate multi-user.target
sudo plymouth-set-default-theme boppos
sudo plymouthd --debug --debug-file=/tmp/plymouth.log
sudo plymouth --show-splash
sudo plymouth ask-for-password --prompt="Enter disk passphrase"   # the passphrase dialog; type some characters
sudo plymouth display-message --text="Waiting for the disk"
sleep 10
sudo plymouth --quit
sudo systemctl isolate graphical.target
```

Check: pure black background, the mark centred and gently pulsing, the small wordmark at the bottom, dots appearing
as you type, the message text. If the screen stays black, look at `/tmp/plymouth.log` for a script error.
To get back to the previous theme: `sudo plymouth-set-default-theme <old theme>`.

## GRUB

GRUB cannot read `/usr`, so the theme has to be put on the boot partition and switched on from GRUB's
configuration. `boppos-boot-theme` ships a small tool for that:

```bash
sudo bopp-grub-theme status            # what is installed and whether this layout is supported
sudo bopp-grub-theme install --dry-run # show exactly what would change; nothing is written
sudo bopp-grub-theme install
sudo bopp-grub-theme remove            # undo it completely
```

**What it does.** It copies the theme to `/boot/grub2/themes/boppos` and adds one clearly marked block to
`/boot/grub2/user.cfg`. That file is sourced by the Fedora-style `grub.cfg` (the `01_users` section) before the
menu is drawn, which is how this layout is meant to be customised. The block switches GRUB from text mode to
graphics (`terminal_output gfxterm`), loads the font and sets the theme. It is wrapped in
`if loadfont unicode`, so if the font or theme cannot be loaded GRUB just shows its normal menu.

**Safety.** It writes nothing unless `grub.cfg` really sources `user.cfg`; on any other layout it says so and
stops (a conventional GRUB uses `GRUB_THEME` in `/etc/default/grub` and `grub-mkconfig` instead). An existing
`user.cfg` is kept as it is (a `GRUB2_PASSWORD` line, for example) and backed up once as
`user.cfg.bopp-backup-<time>`; files are replaced atomically; running it twice changes nothing.

**Checked against a real machine.** The tests use the `grub.cfg` of a BoppOS machine that was converted from
Bazzite: a Fedora-style `/boot/grub2/grub.cfg` generated by `grub2-mkconfig`, with `terminal_output console`, a
`load_video` function, and `${prefix}/user.cfg` sourced from `01_users`; `bootupd` is not installed there, so nothing
rewrites `grub.cfg` or `user.cfg`. If `bootupd` is ever installed and updates GRUB, it keeps `user.cfg`.

If the menu ever looks wrong, `sudo bopp-grub-theme remove` restores the plain one; without the tool, delete the
block between the two `BoppOS GRUB theme` comment lines in `/boot/grub2/user.cfg`.

**Not yet seen on a real boot.** Please run `install --dry-run` first, then `install`, and look at the next boot.
